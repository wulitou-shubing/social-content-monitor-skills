# 我把“盯账号、听口播、填飞书”做成了两个开源 Skill

这个项目的起点很小。我想把一条视频的口播文案取出来，后来又想让 Agent 盯住几个创作者账号，发现新作品就把标题、链接、互动数据和口播文案存进飞书。

看上去是一条顺滑的流程，真正动手时却会碰到几个很实在的问题。页面上有置顶作品，也有平台推荐的其他作者。同一条内容的分享链接还会变。如果视频下载或识别中途失败，前面已经找到的作品也不该跟着丢掉。

所以我没把它写成一个什么都做的大 Skill，而是拆成了两个。

`video-audio-transcribe` 只管媒体。它读取视频链接、本地视频或录音，用 faster-whisper 识别语音，然后保留带时间戳的 TXT 和 SRT。后面要把听写稿整理成口播文案也可以，原始时间戳稿不会被覆盖。

`social-content-monitor-to-lark` 管的是另一半。它先从创作者自己的作品区找候选内容，再核对作者和稳定内容 ID。确认是基线之后发布的新作品，它才会写入飞书。写入时也不等转写全部完成，而是先留下作品信息和 `pending` 状态，再调用第一个 Skill，最后回填同一条记录。

这个顺序是我最在意的地方。下载失败时，作品信息还在。下一次重试会更新原记录，不会在表里又添一行。没有可转写语音的图文作品也不算失败，它会明确标成 `not_applicable`。

仓库里已经写了抖音、小红书、TikTok 和 YouTube 的平台适配方法。这不等于它会绕过平台限制。遇到验证码、登录验证、频率限制或私密内容时，流程会停下。它也不会代替用户点赞、关注、评论或发私信。

两个 Skill 遵循 Agent Skills 开放格式。我用 skills.sh CLI 从一个空目录做过完整安装测试，它能找到并安装仓库里的两个 Skill。最简单的安装方式只有一行。

```bash
npx skills add wulitou-shubing/social-content-monitor-skills
```

Claude Code、Codex 和其他能读取 `SKILL.md` 的 Agent 也可以直接加载它。客户端能读 Skill，不代表自带浏览器、飞书连接器和定时任务，仓库的兼容性表也把这些条件分开写了。

我还放了一份完全虚构的脱敏演示。它能看出飞书里最后会留下哪些字段，也能看出一条视频从发现到回填的顺序，但其中没有真实账号、飞书链接、Cookie 或下载内容。

如果你只需要把一条视频转成文字，只安装第一个就够了。如果你正在做内容跟踪、竞品研究或创作者资料库，可以试试两个配合。新平台的适配、安装问题和失败样本都欢迎提 Issue。
